# 地形观感成熟度差距诊断 — 2026-08-02

**触发**：用户反馈「瓦片/地形渲染板块不像一个成熟的地球引擎」。经澄清，扎眼的是两类：
**① 几何/地形质感差**、**② 加载期不体面**。本文是差距诊断 + 首项修复的设计。

**结论先行**：① 有单一确凿根因（整条高度链被钉死在 65×65），量级足以独立解释观感，
且**源数据已在内存里**，属工程可解；② 目前只有候选、无证据，需真机测量后才排序。

---

## 一、几何/地形质感：根因 = 整条高度链钉死 65×65

### 1.1 链路（逐层追到 GPU，闭合）

| 环节 | 位置 | 实际分辨率 |
|---|---|---|
| 数据源 | 全球 Terrain-RGB 514px，z6–12 | **16.6 m/px** |
| CPU 烘焙网格 | `HeightmapTerrainContentProvider.cpp:248` `min(tileSize-1, 64)` | 133 m |
| 渲染栅格采样 | `DecodedHeightmapSampler.cpp:64` 同 cap | 133 m |
| **高度纹理** | `TerrainDisplacementTemplatePool.cpp:122` `desc.width = gridSize+1` | **65×65** |
| 顶点位移 | `Renderer.cpp:1221` `kGridSize = 64.0`，`texelFetch` 上限 64 | 133 m |

z12 瓦片在重庆纬度（φ≈29.56°）地面宽 `40075017·cos φ / 2¹²` = **8510 m**，
除以 64 格 = **每顶点 133.0 m**。源数据 514px（borderInset 0.5 → 512 有效格）
= **16.6 m/px**。

> **8 倍的高程细节被解码后留在 CPU（`retainedHeightmap` 保全分辨率 514²），
> 从未上过 GPU。**

几何又 cap 在 native z12（`heightmapMaxNativeZoom=12` + `decoupleImageryFromGeometry=true`），
推近不会变细。

### 1.2 为什么当初 cap 到 64（不是拍脑袋）

`HeightmapTerrainContentProvider.cpp:241-247` 的注释说明：514 源建 513² = 26 万顶点/片，
**CPU decode 主线程 O(N²) prep 从 ~4ms 涨到 44–110ms**。cap 到 64 是为了解这个。

**但这个理由只覆盖 CPU 烘焙网格。** 高度纹理和位移模板是**共享的 GPU 侧资源**，
与 decode prep 成本无关 —— 二者本应解耦，现在被同一个常量 `kTerrainDisplacementGridSize`
绑在一起。这是本次诊断认定的**架构错误耦合点**。

### 1.3 观感换算

demo 默认相机 `kMeasureHeightMeters = 1500`、`obliqueElevation = 45°`、
垂直 FOV 60°（`Camera.cpp:24`）。斜距 ≈ 1500/sin45° = 2121 m；
1080 高屏每像素 9.70e-4 rad → 垂直footprint 2.06 m，投到 45° 地面 ≈ **2.9 m/px**。

**一个 133 m 的三角形横跨约 46 个屏幕像素**（2400 高屏则 ~100 px）。
同时影像走 page store 贴到 z14–17 —— **纹理清晰、山体低模**，这就是"不像成熟引擎"
最直接的来源。

参照系：Cesium World Terrain（quantized-mesh 自适应 TIN）有效 ~10–30 m；GE 更细。
**我们比参照系粗一个数量级。**

### 1.4 放大器：着色用逐三角形平法线

`Renderer.cpp:1098-1105`（非实例化）与 `Renderer.cpp:1303-1309`（实例化）：

```glsl
vec3 reliefN = cross(dFdx(v_position), dFdy(v_position));
```

屏幕空间导数叉积 = **逐三角面的 flat normal**，不是插值法线。在 46px 的三角形上，
每个面一个亮度台阶 —— 把低模折射得更刺眼。

这两条叠加即"几何质感差"的完整解释，不需要找第三个原因。

### 1.5 顺带确认不存在的东西

- 无阴影、无 AO（`ssao` / `ambientOcclusion` 全库零命中）
- 光照对比度很低：`base·(0.72 + 0.28·directional)` 半球光

**优先级判断**：在几何还是 133 m 的前提下加阴影意义不大，列为第二梯队。

## 二、加载期不体面：候选 → **已实测定案**（结论见 §2.1）

已开的机制不少（`MinimalGlobeDemoConfig.cpp`）：fill 代理、`cullRequestsWhileMoving`、
geomorph、祖先影像 scale-bias 复用、`preloadAncestors/Siblings` 均为开。
**不是"什么都没做"**。三个候选按怀疑度：

1. **LOD 切换恒为硬 pop**。`enableLodTransitionPeriod = false`，**刻意关的** ——
   注释写明开了会导致每帧 fade discovery + kick-keeps-fading 使运动期工作集膨胀 = 卡顿。
   即 fade 与"不卡"目前二选一，没做成正交。**设计债，不是 bug。**
2. **每帧提交闸门可能偏紧**。demo `mainThreadLoadingTimeLimit = 4.0 ms`，
   经 `TileFrameResourceBudgetPlanner.h:97` 换算 = 每帧 2 次地形 finalize + 7 次影像上传。
   30fps 下 = 60 地形/s。一屏需 60–150 张则收敛数秒。
   **与"停手后 ~4s"量级吻合，但这只是算术自洽，不是证据。**
3. **fill 代理只有 16×16 椭球格**。地形未到时是全平滑球面贴影像，山区真实地形到达时
   "隆起"幅度很大，产生一次显著形变。

### 判据（已执行，见 §2.1）

钉死相机（`freezeCamera` / `scriptedPan` 已有现成设施），清缓存冷启动，抓 `EarthPerf`
头行 `rasterUploadsUsed / maxRasterUploadsPerFrame` 与 finalize 计数的**逐帧序列**：

- 每帧打满上限 → 闸门问题（候选 2 成立）
- 未打满 → 瓶颈在网络或 mapping，方向完全不同

**候选 2 和 3 不靠猜排序。**

> 实测发现这条判据本身**漏了一个分支**：还存在"既不打满、也不是网络瓶颈"的第三种
> 情况 —— 预算根本没被消费（更上游的硬闸早退）。见 §2.1。

### 2.1 实测（2026-08-03，release，真机 7e045e39，冷缓存）

**仪器**：新增 `LoadGate` 逐帧行（`GLESView.cpp`，与 `LoadQual` 同一采样门 ——
暂态逐帧、稳态 120 帧心跳），打 `fin=用/上限 rasUp=用/上限 ms=用/上限
pend=请求/上传/终态 net=… prog=… mode=交互态/平滑态`。

**方法**：每轮 `adb uninstall` + `install`（清 HttpCache）→ 启动 → 静置 ~20s 让
初始视图收敛 → 施加运动 → 静置测排空。全程 logcat 流式落盘。

⚠️ **第一轮作废并重做**：原打算"钉死相机静置冷启动"，但 CamPose 显示 pitch
−45°→−22°、camH 1500→6234m，且 logcat 里有系统 `GestureLog` 与 `GESTDIAG
dragStart` —— 手机被真人碰了。**判据必须自带污染检测**：先看 CamPose 是否漂、
再看有无 GESTDIAG。第二轮改用**确定性输入**
`adb shell input keyevent 25`（音量下 = `nativeDebugZoom(0.84)`）×14
—— 触摸注入不可用（`adb shell input swipe` 引擎侧收不到，GESTDIAG 为 0）。

#### 结果（Run C，确定性，交互 3.82s）

| t | mode | fin | rasUp | pendUp |
|---|---|---|---|---|
| 26.1s | `--` | 0/20 | 0/20 | 0 |
| 28.2s | `IS` | **0/2** | 0/7 | 5 |
| 30.2s | `IS` | **0/2** | 0/7 | **49** |
| 32.2s | `-S` | **2/2** | 0/7 | 45 |
| 34.2s | `--` | 0/20 | 0/20 | **0** |

- 交互期 **136 帧里 finalize 被使用 0 次**（不是"打满"，是**根本没走到预算**）
- 积压 `pendingGltfTerrainUploads` 随交互时长线性涨：0 → 49（≈13/s）
- 交互一结束立刻 `fin=2/2` 打满 → 49 条 **0.71s 排空**

Run A（真人手势，连续交互 29.6s）同一签名、量级放大：交互期 **0/538 帧**使用
finalize，积压峰值 **386**（≈24/s），停手后 **2.01s** 排空，排空期
57/200 帧打满、`ms` 一度到 **4.10/4.00**（主线程时间预算超支）。

#### 根因

`TilePendingLoadQueue.cpp:149`：

```cpp
if (context.interactionActive &&
    bestIt->first.group != TileLoadPriorityGroup::Urgent) {
    return std::nullopt;   // ← 早退发生在 tryFinalize 之前
}
```

交互期**只放行 Urgent（当帧选中渲染的近景瓦片）**，Preload/Normal 的上传被硬冻结，
预算对象连碰都没碰到。积压在停手瞬间一次性泄出，由平滑期 2 次/帧的闸门排空 ——
这才是"停手后暂态"的成因链。

**对照：影像侧早就不这么干了。** `RasterOverlayTileProvider.cpp:88-108`
`uploadAllowedDuringInteraction` 的注释写明它**已经**从"mapped-raster 前缀无条件排除"
改成了"只按单次上传成本过滤，节奏交给 budget lane 涓流"，理由正是"长交互把影像上传
全量积压，交互期影像完全停更"。**地形侧从未做同样的改造** —— 这是一处架构不对称，
不是参数没调好。

> 与已有记录的关系：`ge-loading-experience-gap-2026-07-17` 早就把"拖动期 Urgent-only
> 上传冻结"列为根因之一。本轮**不是新发现，是把它量化并锁死**（积压速率、峰值、
> 排空时长、闸门消费率），并定位到具体早退语句与影像侧的对照修法。

#### 候选结论

| # | 候选 | 判定 |
|---|---|---|
| 1 | LOD 硬 pop | 本轮未测，仍是设计债 |
| 2 | 每帧提交闸门偏紧 | **部分成立，但根因不是它**。交互期预算完全没被消费（冻结在更上游）；只有**排空期**闸门才是限速器（`fin=2/2` 饱和、`ms` 超 4ms） |
| 2b | 影像上传闸门 | **证伪**。`rasUp` 在三轮运行中**从未打满**（非交互期仅 10–14 帧有非零使用）。影像不是瓶颈 |
| 3 | fill 代理 16×16 | **本轮不成立**。稳态残留的 2 个 fill 命令是 `geoZ=2-12` 里 z2–z5 的瓦片 —— 地形源 z6-12，低于 `minimumZoom` 走椭球回退是**正确行为**。`LoadQual` 的 `dirty` 启发式把它算成脏，是误报 |

#### 顺带确认：默认钉死视角测不出加载问题

初始视图（重庆 1500m / pitch −45°）稳态只有 **vis=3** 张 z12 瓦片，冷启动几秒内
`sharp=3 miss=0 dirty=0` 全干净、`pendUp` 恒为 0。**这个场景结构上无法暴露任何加载
暂态**，必须主动制造运动才有信号 —— 与 §4b.4"钉死场景无法验收 relief 着色"是同一类
教训：**验收场景本身要先证明它能显示待测现象。**

### 2.2 修复与 A/B 验收（commit `294bff2ed`）

**改动**：删掉 `TilePendingLoadQueue::takeHighestPriorityUpload` 里的
`interactionActive && 队首非 Urgent → 早退`（4 行）。Urgent 仍排最前，只是不再独占；
交互期节奏改由 budget lane 限（平滑期 4ms → 2 次/帧）。就是影像侧
`uploadAllowedDuringInteraction` 早已做过的那次改造。

**验收**：`tools/load_ab/`（自动化台，release，冷缓存，各 5 轮，确定性 keyevent 输入）

| 判据 | before | after | 判定 |
|---|---|---|---|
| ① 交互期积压峰值 | 48 [43–51] | **0 [0–0]** | PASS（目标 ≤10） |
| ② 停手 → 归零时长 | 0.53s [0.27–0.55] | **0.00s [0–0]** | PASS（目标 ≤0.2s） |
| ③ 交互期慢帧率 | 0.39/s [0.37–1.14] | 0.75/s [0.39–1.50] | **INCONC**（p=0.524） |
| 机制信号：交互期 `fin>0` 帧数 | 0 [0–0] | **15 [7–28]** | 闸确已放开 |

①② 五轮无一例外。③ 名义超阈值（≤1.20×），但中位数差的双侧置换检验
（n=5+5 穷举精确）给出 **p=0.524** —— 与调频噪声不可区分。绝对量级约为
5s 拖动多出 2 个 ≥25ms 帧。用户拍板接受。

> **测量台由此改过一次**：原先只比中位数的 ≤1.20× 规则会把这个差值判成 FAIL。
> 改为三态（PASS / FAIL / INCONC），超阈值但 p≥0.05 判 INCONC 并提示加大 n。
> **一个在样本撑不住时还硬发 FAIL 的判定器，比没有判定器更坏** —— 它会让人
> 去"修"一个不存在的回归。见 commit `646013c13`。

**顺带一个量级观察**：只用 15 帧（约占 300 帧交互期的 5%）就吃掉了全部 48 条积压。
这活本来就没多少，以前只是被整段冻着。

**遗留**：`PendingLoadFinalizeContext::interactionActive` 与
`takeHighestPriorityUpload(bool, budget)` 的 bool 形参已无人读取，但涉及 ~80 处
测试调用点，属独立的机械清理，未并入本次改动。

## 四、本次实施：法线与几何解耦

### 4.1 一处修正（相对初版口头方案）

初版说"法线改逐像素、从高度纹理算 → 光影能到纹理分辨率"。**这句在当前代码下不成立**：
高度纹理本身就是 65²（§1.1），从它算逐像素法线只能得到**平滑**，拿不到细节。

于是有两条路：

| | 做法 | 得到 | 代价 |
|---|---|---|---|
| **2a** | 片元中心差分现有 65² 高度纹理 | 只去掉刻面，**无新细节** | ~12 次 texelFetch/片元；且 §三-2 落地后要重写 |
| **2b** | **CPU 从全分辨率 514² 烘法线贴图，硬件双线性采样** | 去刻面 **+ 8× 真实光影细节** | 1 次 fetch/片元；新增 CPU bake + 纹理数组 + 绑定 |

**选 2b。** 理由：
- 2b 在质量与**运行时开销**上都严格优于 2a（1 fetch vs 12）
- 2b 才是初版承诺的产出（"光影到纹理分辨率"）
- 2b 是成熟引擎的标准做法（法线贴图使**着色分辨率与几何分辨率解耦**），
  且与 §三-2 正交 —— 几何抬到 256 后这套法线链路不用改
- 2a 是纯技术债：省下的工时会在 §三-2 时连本带利还

**工时修正**：初版估 2–4h（那是 2a 的量）。2b 在 AI 协作基准下约 **1 天**，含真机 A/B。

### 4.2 设计

**CPU 侧**：解码 heightmap 后，从**全分辨率**栅格烘一张切空间法线贴图。
分辨率取 `kTerrainNormalTextureSize`（初值 257，即几何的 4×；上限由源 514 决定）。
编码 RG8：法线在瓦片切空间 `(east, north, up)`，因 `nz > 0` 恒成立，
只存 `(nx, ny)·0.5+0.5`，`nz = sqrt(1 − nx² − ny²)` 重建 —— 省一半显存。

**GPU 侧**：新增 `kGltfTerrainNormalTextureSlot = 23` 与 `normalArray_` 纹理数组
（LINEAR 过滤 —— 与高度纹理的 NEAREST 不同，法线可以硬件插值，这正是 C0 平滑的来源）。

片元里重建切基：位移沿 `up = normalize(v_normal)`，令
`S_u, S_v` 由屏幕导数 2×2 反解得到，投掉 up 分量得 `e_u, e_v`，
则 `N = normalize(up·1 − g_u·e_u − g_v·e_v)`，其中 `(g_u, g_v)` 即贴图解出的坡度。
**无需新增 uniform 传瓦片尺寸/切向量。**

**退化路径**（保持现状，零回归）：
- `u_heightDisplace.z <= 0.5`（椭球回落 / fill 代理 / 无高度纹理的上采样片）
- 裙墙片元（新增 `v_skirt` varying；裙墙位移为 0，法线应保持墙面朝向）
- 2×2 反解行列式趋零（掠视/轮廓边）

三者一律回落到现有 `dFdx` 路径。

**实例化路径**：法线层号放 `i_layers.w` —— 该槽当前是 `_` 未用，正好一个空位。

**已知取舍**：geomorph 过程中几何在粗↔细之间，而法线贴图恒为细 —— 着色比几何"超前"。
视觉上是好事（细节先到），且 Cesium 同样如此。记录不修。

### 4.3 验收判据（二元）

1. **机制信号**：地形片元采样法线贴图的分支被走到 —— 诊断计数 / RenderDoc 帧抓
2. **像素判断归用户**：钉死 §1.3 场景（1500m / 45° / 重庆），A/B 截图对比，
   由用户判定刻面是否消失、坡面明暗是否出现 16.6m 级细节
3. **性能**：**release 构建**下同场景帧时不劣化超过噪声带（见 `perf-measured-on-debug-build`）

### 4.4 实测结果（真机 Adreno / debug 构建）

**判据 1（机制）：通过。** 临时探针把命中法线贴图分支的片元涂纯红 →
**93.47% 屏幕像素为红**，即整片地形都走了新路径（纹理绑定、uniform 层号、
GLES 单元映射全部正确）。

**判据 2（像素）：法线确实变了，但画面几乎没变 —— 原因不在本改动。**

逐项探针（同场景，输出到 RGB 通道后统计）：

| 量 | 中位 | p95 |
|---|---|---|
| 新旧法线夹角 `\|N_new − N_old\|` | ≈ 3.0° | > 12° |
| `ΔNdotL` | 0.009 | — |
| **`directional = smoothstep(0,1,NdotL)`** | **0.992** | — |

**根因：demo 钉死的太阳几乎在天顶，`directional` 死死钉在 smoothstep 的饱和顶端，
而 `smoothstep` 在 x=1 处导数恰为 0。** 于是无论法线怎么变，着色都不响应 ——
改动前后整屏只有 0.16% 像素有差、最大差 12/765。

把太阳压低（`kFixedSimulationJulianDate + 0.18`，临时，已还原）后重测：
`directional` 中位降到 0.18（进入响应区），`ΔNdotL` 中位升到 0.031，
A/B **30.1% 像素发生变化** —— 路径确实在工作。

**但幅度仍然很小**：mean 3 / p95 11 / max 59（三通道求和，满值 765），
即逐通道 p95 仅 ≈ 4/255 的亮度变化。算术自洽：
`Δcolor ≈ base × 0.28 × (dsmoothstep/dx) × ΔNdotL ≈ base × 1%`。

**判据 3（性能）：debug 构建下 `Engine.render.total` 7.94ms vs 基线 7.75ms**，
落在单次 run 的 DVFS 噪声带内（见 `device-dvfs-frame-time-noise`）。
**release 下的正式测量尚未做。**

### 4.5 由此暴露的新根因：地形基本没有被着色

上面的数字改变了 §1.4 的判断。原以为"逐三角面平法线 → 46px 刻面"是质感差的
放大器；实测表明**在当前光照模型下，刻面本身也几乎看不见 —— 因为地形的方向
光照贡献总共只有 ~1% 亮度变化**：

```glsl
color = base·(0.72 + 0.28·directional)·sunTint + base·ambient·(1−directional)
```

方向项振幅只有 0.28，且 `smoothstep` 在高太阳角下饱和归零。**地形的明暗几乎
完全来自影像自带的烘焙阴影，引擎自己的 relief 着色是装饰性的。**

这是与 §1.1 几何钉死**相互独立**的第二个根因：
- 几何 133m → 起伏被抹平（几何问题）
- 光照振幅 ~1% + 高太阳角饱和 → 仅存的起伏也照不出来（着色问题）

**法线贴图（§四）是必要基础设施，但它的收益被这一条完全闸住。** 顺序上，
光照模型的动态范围应当先于 §三-2 的几何解锁处理 —— 否则把几何抬到 16.6m 也
同样照不出来。

**光照常数（0.72/0.28、smoothstep 曲线、是否引入地形自阴影）是观感取向决策，
不由本次改动单方面改动**（判据 2「像素判断归用户」）。列为待拍板项。

## 四之二、参考实现调研（`.ref/` 本地源码，非记忆）

用户拍板：法线贴图（§四）**回退**（patch 存档），光照**按正式版地球引擎的策略做**。

### 4b.1 三方对照

| | 法线来源 | 光照曲线 | 方向项动态范围 |
|---|---|---|---|
| **CesiumJS** | 逐顶点 octencoded（quantized-mesh 格式自带） | `clamp(NdotL·0.9 + 0.3, 0, 1)` **线性** | **0.3 → 1.0（3.3×）** |
| **osgEarth** | **法线贴图，默认开，256²/瓦片** | Phong `max(dot(N,L),0)` **线性** | 全范围 |
| **本引擎（改前）** | 逐三角面 dFdx 叉积 | `0.72 + 0.28·smoothstep(NdotL)` | 0.72 → 1.0（**1.39×**） |

出处：
- `.ref/cesium-js/.../Shaders/GlobeFS.glsl:438`（`ENABLE_VERTEX_LIGHTING` 路径）
- `.ref/cesium-js/.../Scene/Globe.js:176,379`（`lambertDiffuseMultiplier=0.9`、
  `vertexShadowDarkness=0.3`）；`Globe.js:166` **`enableLighting = false`——
  Cesium 出厂globe 是不打光的**，明暗全靠影像自带烘焙
- `.ref/osgearth/src/osgEarth/TerrainOptions:28,29,46`
  （`useNormalMaps=true`、`normalMapTileSize=256`、`minNormalMapLOD=0`）
- `.ref/osgearth/src/osgEarth/PhongLighting.glsl:125`（`NdotL = max(dot(N,L),0)`）

**两个参考实现在两点上一致、而我们两点都不同**：曲线用线性而非 smoothstep；
范围比我们大 2.4 倍。

> 附带结论：osgEarth 默认就开 256² 地形法线贴图 —— **§四被回退的那套架构正是
> 生产引擎的标准做法**，且它选的贴图边长（256）是本次初值（128）的 2 倍。
> 将来若重启，应按 osgEarth 取 256。

### 4b.2 已实施

四处地形着色（GLSL 非实例化/实例化 + MSL 两份镜像）统一改为：

```glsl
directional = clamp(NdotL * 0.9 + 0.3, 0.0, 1.0);   // = Cesium 系数
sunlit      = clamp(NdotL, 0.0, 1.0);               // 冷暖/ambient 分配,端点语义不变
color = base·directional·mix(1, sunTint, sunlit) + base·ambient·(1 − sunlit)
```

`ctest 161/161` 通过。

### 4b.3 实测：**默认场景下依然几乎不变**

| A/B | 变化像素 | 平均亮度 |
|---|---|---|
| 默认太阳（demo 钉死场景） | **8.37%** | 101.0 → 101.5 |
| 低太阳（`+0.18` 日，临时） | **99.74%** | 83.8 → 62.5，对比度 3.90 → **4.76** |

原因与 §4.4 同源：钉死场景 NdotL ≈ 0.99，
`0.72+0.28·smoothstep(0.99) ≈ 0.9999` 与 `clamp(0.99·0.9+0.3) = 1.0` **都饱和到 1**。

### 4b.4 由此确立的总结论：**钉死场景无法验收任何 relief 着色**

三次独立测量指向同一件事：

1. 法线贴图（法线中位改变 3°）→ 画面变 0.16%
2. 光照曲线换成参考实现（动态范围 ×2.4）→ 画面变 8.37%
3. 两者在低太阳下都立刻产生大幅变化（30.1% / 99.74%）

**demo 钉死的太阳几乎在天顶 ⇒ 全屏 NdotL ≈ 1 ⇒ 任何法线来源、任何光照曲线都
产出同一个饱和值。** 叠加 §1.1 的 133m 几何把坡度抹平，这个场景在结构上就
测不出地形质感。

> **因此：`kFixedSimulationJulianDate` / 相机构成的验收场景必须先修，
> 否则后续每一项质感改动都会测出「没变」。** 这一条现在排在所有质感工作之前。

**待用户拍板**：新光照在低太阳下把地形整体压暗（平均 83.8 → 62.5，
阴影底从 0.72 降到 Cesium 的 0.3）。这是范围拉开的必然代价，是否可接受属观感取向。

### 4b.5 验收场景已修（用户拍板：太阳改斜射角）

用引擎自己的太阳模型（`SunDirection::cosIncidence`，逐行复算）扫偏移量，
重庆（106.508E, 29.617N）：

| `kFixedSimulationJulianDate` 偏移 | 太阳高度角 | NdotL | 方向项 |
|---|---|---|---|
| **0.00（原值）** | **71.4°** | 0.948 | **1.000（饱和）** |
| +0.08 | 46.8° | 0.729 | 0.956 |
| **+0.12（新值）** | **34.3°** | 0.564 | **0.808** |
| +0.18 | 16.0° | 0.275 | 0.547 |

**饱和上界：高度角 ≥ 51°（NdotL ≥ 0.778）方向项即重新 clamp 到 1.0，勿调回。**

**验证（决定性）**：把**同一个**光照改动分别放在新旧两个场景下 A/B ——

| 场景 | 变化像素 | mean | p95 |
|---|---|---|---|
| 旧场景（太阳 71.4°） | **8.37%** | 1.59 | 4.0 |
| 新场景（太阳 34.3°） | **96.15%** | 22.98 | 54.0 |

同一份代码改动，仅因太阳角修正，可观测性差了 **11.5 倍**。
**§4b.4 的结论就此闭环：旧场景在结构上无法验收任何 relief 着色工作。**

后续所有质感改动（几何解锁 §三-3、法线贴图重启）都应在新场景下 A/B。

## 五、顺带发现（**不在本次改动范围**）

`RenderDeviceMetal.mm:1114` `maxMaterialTextures = kGltfPageStoreIndirTextureSlot + 1`
= 22，绑定循环只覆盖槽 0–21；而 `kGltfHeightTextureSlot = 22`
（`RenderCommand.h:31`）。即 **Metal 后端从未绑定地形高度纹理**，
而 `kTerrainVertexMSL:3071` 声明了 `[[texture(22)]]` 并在
`u_heightDisplace.z > 0.5` 时读它 —— Metal 侧地形 GPU 位移形同休眠。

与既有记忆「Metal Step4 主动挂起」一致，**大概率是已知的挂起状态而非新 bug**，
但绑定循环上界与槽常量的这处错配值得单独确认。**本次只提示，不修 Metal 位移。**

（本次确实动了该上界一行：改成 `kGltfTerrainNormalTextureSlot + 1`，否则新增的
槽 23 会被同样排除出绑定循环 —— 这是"新增最高纹理槽必须同步扩容"的既有约定，
不是在修 Metal 位移。副作用是槽 22 也开始被绑到 fragment 表，片元不声明不读，惰性。）

**已知镜像发散（本次有意不动）**：`kTerrainInstanced{Vertex,Fragment}MSL` 自称是
GLSL 实例化对的镜像，但在 `Renderer.cpp` 里被 `(void)` 掉、从不编译。本次改了
GLSL 实例化对而**没有同步这两个死字符串** —— 因为无法编译验证的镜像代码比明写的
发散更危险。将来接线 Metal 实例化时需一并补上法线贴图分支。

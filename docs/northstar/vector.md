`docs/issues/` 是写完即冻结的历史档案;**本文是活的**,随每次专项收官更新。

也不回答「怎么搭的、要扩展该动哪」——那是 **`docs/mvt-vector-architecture.md`**
(数据流 / 分层 / 六条契约 / 扩展指南 / 架构层面的得失)。两文互补:
本文给判据编号,那份给机制与扩展点,判据不在那边重复。

## 怎么用(这是本文的主要价值)

- **判据编号(V1…)是稳定引用锚点。** 你可以直接说「V3 我不满意」「V9 提前做」,
  不必重新描述一遍观感;我开工前会引用「本次动 V3/V4」,收官后改状态并附证据。
- **状态**:✅ 达成(有证据) ⚠️ 部分达成/有已知缺口 ❌ 未做 🔒 待你拍板
- **类型决定谁说了算**:
  - 【机制】我能自证 —— 命令输出、计数、测试红绿、帧时。我负责给数,不需要你看。
  - 【观感】像素判断**归你** —— 我只负责钉死复现场景 + 给截图,不替你判定"好看"。
- **「代价」列是硬要求**:每条体验都要写清花了多少(GPU/CPU/内存),因为你认可的
  准则是「体验达标**且最便宜**」——只写达没达成,就没法判断值不值、还有没有余量。
  **没量化过就写「未量化」,不许填"应该很小"**;这类空头承诺会沉淀成 C.5 的债。
- **性能债编号(P1…)** 与判据编号同为引用锚点,见 C.5。
- **改状态必须附证据**(commit / 真机数据 / 截图),不能凭印象改。
- **`推断` 标记**:凡带此标记的判据是我从现状与对照系推出的,**不是你说过的**,
  优先请你校对——校错了比没写更糟。

## 北极星一句话

> 在 **45° 斜视 + 地平线在屏**的 3D 地形上,线的观感**超过 maplibre 的任何一种模式**:
> 拿到平面模式的线宽恒定与锐度,同时不付平面模式"没有 3D"的代价,
> 也不落进地形 RTT 模式"两次重烘之间线宽在漂"的病。

**这不是口号,是机制差异,已在 `.ref` 源码核实**(见下方对照表)。
对照系为什么是 maplibre 而不是 Google Earth:GE 的矢量是预烘影像,
我们要的是**运行期可换样式/可编辑**的矢量,GE 那条路不可比。

### 水位线对照(三方)

| 维度 | maplibre 平面模式 | maplibre 地形 RTT | **本引擎** |
|---|---|---|---|
| 线宽随相机连续恒定 | ✅ 屏幕空间逐帧画 | ❌ **两次重烘之间是位图拉伸** | ✅ **FS 内逐像素解析解算** |
| 重烘触发 | 不需要 | 源瓦集合/数据版本变才重烘,**指纹不含 zoom** | **不需要**(z 封顶后零重烘) |
| 3D 地形贴合 | ❌ 没有地形 | ✅ | ✅ |
| 任意俯仰角 / 地平线在屏 | — | 受限(病被放大故回避) | ✅ 45° 斜视为默认姿态 |
| 放大时锐度 | ✅ 矢量重画 | ❌ 纹理放大糊 | ✅ SDF 解析放大(**V5 有余债**) |
| GPU 成本 | 独立 draw | 独立 RTT pass + FBO | **~0(寄生地形 FS)** |

> **关键出处**:`.ref/maplibre-gl-js/src/webgl/render_to_texture.ts:114-127` ——
> RTT 失效指纹 = `sorted_tile_keys#revision`,**只含源瓦集合与数据版本,不含 zoom
> 或任何相机参数**。故 z14.0 连续推到 z14.9 的全过程 RTT 不重烘,线宽按纹理比例
> 放大 = 屏幕像素不恒定。这是它的结构性病,不是参数没调好。

### B.1 V24 排查记录(2026-08-15,未结案)

### B.2 换代代码排查(2026-08-15):线与点走的是两条路,只有一条有保护

查 `VectorTileTree` / `MvtVectorSource` / `RoadFieldSource` 后的**结构性发现**:

| | 线(路网) | 点 / 标注(+ drape 面) |
|---|---|---|
| 取瓦 | `RoadFieldSource` **直接问 `MvtTileFetchCache`** | `MvtVectorSource` → **`VectorTileTree`** |
| 表示 | pageStore 场页(z 封顶) | 逐瓦网格 + 符号实例 |
| 换代保护 | 两级锚页预暖、z 封顶零重烘 | **无迟滞、无后代回退、无保活** |

> **`VectorTileTree` 不参与线的渲染。** 这条以前没写清,导致 V12(拉远/换代时线
> 不整片消失)拿场页锚页预暖当证据标 ✅ —— 对线成立,但**同一句话对点从不成立**,
> 而点走的是完全没保护的另一条路。这是 E3「兜底路径冒充主路径」的同型问题:
> **一层的修复被记在了一条跨层判据的账上**。

**四个缺陷,三个已由 host 测试钉死**(`tests/unit/data/test_vector_tile_tree.cpp`,
测试**钉的是当前缺陷行为**,修好后会红 —— 那时改判据,别改测试迁就实现):

| # | 缺陷 | 位置 | 证据 |
|---|---|---|---|
| **①** | **zoom 选择无迟滞**:`floor(log2(4e7/h))` 硬切,视高抖 ±0.5% 就翻档 | `VectorTileTree.cpp:31-37` | `ZoomHasNoHysteresisAtBoundary`:20 次微抖 → **20 次全翻档**,零死区 |
| **②** | **只有祖先回退,没有后代回退**:拉远时粗瓦未加载 → 渲染集**空**,哪怕细瓦还在缓存、几何完全够覆盖 | `.cpp:94-104`(只 `parent()` 向上走) | `ZoomOutHasNoDescendantFallback`:z14 喂满后拉到 z11,`renderTiles` **空** |
| **③** | **出渲染集一帧即成淘汰候选** | `.cpp:204`(`lastUsedFrame < frame_`) | `TilesLeavingRenderSetAreImmediatelyEvictable`:超预算后原渲染瓦被淘汰 → 抖回来要重拉 |
| **④** | **drop 无限速 / commit 限速 4**:出集瓦**一帧全掉**,新瓦每帧最多 `maxTileCommitsPerUpdate=4` 个进 | `MvtVectorSource.cpp:148-176` | 未单测。视口上限 `maxTilesPerView=64` → 整片换代最坏 **16 帧 ≈267ms** 才补齐 |

**①+④ 是"闪"的主机制**:边界抖动触发整集换代,而换代天生不对称(旧的瞬间没、
新的慢慢来)。**②+③ 是"浪费"那一半**:抖回来时数据已被丢弃,必须重镶/重拉 ——
正好对上你说的「闪 = 可能在浪费」。

### B.3 R* 落地(2026-08-15,同日根修)

**方案 R\* = 置换式细化 + 全有全无回退 + 置换单元原子换手**,一次吃掉缺陷
②③④⑤(①迟滞降级为"省重算",见下)。语义对拍本仓库地形 Tileset 的
replacement refinement 与 maplibre `_updateRetainedTiles`,但比 maplibre 多
"无重叠"保证 —— 世界空间渲染无逐瓦 stencil,祖先与子瓦同框即要素重影,
maplibre 靠裁剪掩、我们靠**选择层不产生重叠**。

| 层 | 改动 | 消掉 |
|---|---|---|

### B.6 POI 锚点高度陈旧(2026-08-15,"幸福广场闪一下就没")

**用户判别域**:初始视角该有的标记点闪一下就消失;缩放后又出现。

**排查中作废两轮 A/B,原因都值得记**:
1. 关 `runTerrainDepthPrepass` → 仍消失。**该轮无效**:它只关掉 shader 侧
   遮挡淡出,而符号命令 `cmd.depthTest = true`,**硬件深度测试还在**。
2. 改 `cmd.depthTest = false` → **闪退**。`MVP render command validation
   failed: Vector* depthTest violates MVP fixed state` —— depthTest 属 MVP
   固定状态,有校验器守着。守卫响得对,abort message 直接点名违规项。
3. 改用恒定 `u_depthPushNdc`(不碰固定状态)→ **从"必消失"变成"有时消失"**,
   证实深度掩埋是成因之一,底下还压着一个竞态。

**根因**:`buildRenderCommands` 的贴地重钳(地形代次变化 → 重采高度)
**只遍历 `buckets_`,漏了 `tileBuckets_`** —— 而 POI 符号正是瓦片桶。
锚点停在 commit 当刻的粗地形高度上,地形细化后山体升上来把它埋掉,
硬件深度与 T2 判定一起吃掉符号。`commitTileMesh` 的原注释写着
「山地下可能被地形遮挡吃掉,属加载瞬态;**瓦片换代重 commit 时自愈**」——
这个假设错了:瓦片换代只有缩放才触发,静止加载期不会发生。
**"闪一下就没"与"缩放后才出现"是同一个因的两面。**

**修**:`BucketGpu` 留 `tileSymbolSources`(rank 截断后,容量同上屏上限
128/瓦);抽出 `buildTileSymbolGpu` 给 commit 与重钳共用(两处各写一遍必然
错位);新增 `reclampTileBucketSymbols` 在地形代次变化时重采锚点高度、
重建点 buffer 并重烘标签(锚点变了 glyph quad 的 rel 也变)。

**"有时消失"不是第二个成因**(2026-08-15 复看后收口):三轮观察由同一根因
解释 —— A/B1 是硬件深度**硬测试无容差**,锚点低一点就挡死,故必消失;
A/B3 绕过硬件深度但 T2 仍在,而 T2 带 **60m bias**,只有高程误差 >60m 才
全灭,**误差多大取决于 commit 当刻地形有多粗 = 随加载时序变**,故"有时"。
修后锚点不再陈旧,两条路径都没得吃。**用户复看:稳态正常。**
先前把它判为"另有竞态"是判断过度,记此以免再开无谓排查。

**可复用教训 —— 派生数据的失效传播漏接**:锚点高度是从地形派生的快照,
地形变了它就过期。store 桶早有重钳(P3 方案 A),**瓦片桶是后加的
(符号刀 A),没接上这条既有失效链**;原注释的兜底假设「瓦片换代重
commit 时自愈」只在缩放时成立,静止加载期不触发。
**新增派生路径时该问:它依赖的上游有失效通知吗?既有消费者怎么接的?**

⚠️ **曾有两份 chongqing.mbtiles**:`scaffold/tmp/`(6.4MB,08-04,层只有
building/roads/water,**无 poi**)与 `tmp/`(10.6MB,08-14,含 poi)。
我查错文件得出过"数据里根本没有幸福广场"的假结论,靠 `lsof` 查 server

### B.4 maplibre 标注为何不闪(2026-08-15,`.ref` 源码核实)

问的是"它凭什么不闪",答案是**四道防线,而不是一个技巧**。逐条对照:

| # | maplibre 机制 | 出处 | 我们(修前 → 修后) |
|---|---|---|---|
| **1** | **opacity 真源不在桶顶点**,在 `Placement.opacities`(按 `crossTileID` 键的 map);桶顶点只是 GPU 镜像 | `placement.ts:185,963-972` | 修前**真源就是顶点**(新桶=0 即真的黑);修后仍在顶点,但 bake 时从 placement 拉取 → **等价** |
| **2** | **新桶到达当帧立即重写 opacity**:`if (placementCommitted \|\| symbolBucketsChanged)` —— `symbolBucketsChanged` 就是"桶变了"这一路,**不等节流** | `style.ts:1897` | 修前**只在节流窗或有 fade 推进时回写** → 换桶后最长黑 300ms = 你看到的硬闪;修后 bake 时直接烘入 → **等价** |
| **3** | **`justReloaded` → `skipFade`**:重载桶上没有历史 id 的符号直接满亮度,不重新淡入 | `placement.ts:819,33` | 我们无此语义:新 id 仍从 0 淡入。**判不跟进**——crossTileID 匹配上的已继承,没匹配上的本就是新符号,淡入是正确观感 |
| **4** | **带符号的瓦离场不立即删**,`setSymbolHoldDuration(fadeDuration)` 持有到淡出结束才移除 | `tile_manager.ts:588-598` | **仍缺**:`toDrop` 里整片离场的瓦立即 `drop` → 标签硬消失无淡出。R* 的原子换手只覆盖"有替换者"那一路。记为 V25 |

**最关键的一条是 #2,而它暴露了一个口径错误**:maplibre 的 300ms(`fadeDuration`,
`map.ts:511`)节流的是 **`stillRecent` → 碰撞重算**(`placement.ts:1268`),
**不是 opacity 回写**。我们把两件事绑在了同一个闸上 —— 碰撞结果在亚秒尺度稳定
所以节流合理,但 opacity 回写是"让 GPU 追上已知状态",没有任何理由节流。
本次修解开了这个耦合。

> 附带一条口径细节(值得学):`stillRecent` 的节流时长带 zoom 修正 ——
> **缩放进行中用满时长(少跑,避免 jank),停下后才缩短(多跑,快速收敛)**。
> 我们是恒定 300ms。真机若见"停手后标注重排慢半拍"再考虑,现无证据。

**性能债(顺带量出来)**:maplibre 的 opacity 是**独立 1 字节/顶点的 buffer**
(`symbol_bucket.ts:174,210-213`,注释明写"performance hack"用 uint32 写 uint8 读);
我们改一次 opacity 要**重传整条 8 float/顶点的标签顶点流(32B/顶点,32×)**。
未量化,记 P8。

## C. 性能北极星(预算 / 实测 / 债)

> **准则**:优化只走「消除浪费」,**不走降低可见细节**——限帧、降 LOD、缩短可见
> 距离都不算优化。矢量三分工的整个架构就是这条准则的产物:面/线的 GPU 成本不是
> 被"调低"的,是被**换了表示**换掉的。

### C.1 帧预算(60fps = 16.7ms) `推断`

| 阶段 | 预算 | 当前实测(2026-08-14 步3 后) | 余量 |
|---|---|---|---|
| FrameLoop total(手势期,无偏采样) | < 16.7ms | **6.9 / 8.1ms**(n=2,见下方采样陷阱) | 大 |
| engine(CPU 侧) | < 6ms | p50 **3.69ms**,max 7.95ms | 有 |
| **慢帧率**(total ≥ 25ms) | < 1% `推断` | **2.1%**(5/241 帧) | **超** → 见 P6 |

| terrain pass(含面+线场解算) | 不高于纯影像基线 | **3.62-4.18ms** vs 刀2 记录基线 3.3ms | 同量级 |
| GPU total(手势期) | < 16.7ms | **7.80-9.02ms**(尖峰帧 13.94) | 有 |

> **⚠️ 采样陷阱(踩过一次,写下来防复发)**:`FrameLoop` 日志的打印条件是
> `frameId<=3 || frameId%120==0 || total>=25ms || swap>=8ms` ——
> **它是异常捕获,不是随机采样**。直接对日志行算 p50 会把慢帧当分母,
> 得出"p50=20.6ms 超标"的假结论(真值 6.9-8.1ms)。只有 `%120==0` 那批无偏。

**预算是我推断的,请校对**:我按 60fps 反推,但你的实际目标可能是 30fps 稳定
优先于 60fps 抖动。这条定不下来,后面所有"还有没有余量"的判断都会偏。

### C.6 P7 容量债量化(2026-08-15)

尺子:`scaffold/tools/line_field_capacity_sim.py`(入库,忠实复刻烘焙+FS 解算)。
数据:重庆 z14 最密三瓦(932/642/641 线,3572/3168/3154 段)。
**判据:只统计穿透 ±0.5px AA 带的错误**——FS 用 `smoothstep(w+0.5px, w-0.5px)`
做抗锯齿,亚像素级偏差本就不可见;用硬阈值统计会把它算成"漏画",
虚高一个数量级(0.040% → 0.380%)。分母 = 该画的像素数。

**漏画率随距离段(texelPx = 2^d,d = 影像页z − 场页z):**

| | 半宽 1.05px(z12 端) | 半宽 2.0px | 半宽 3.15px(z16 端) |
|---|---|---|---|
| texelPx=2 | 0.000% | 0.000% | 0.000% |
| texelPx=4 | 0.346% | **0.055%** | 0.002% |
| texelPx=8 | 1.091% | 0.811% | **0.303%** |
| texelPx=16 | — | — | **1.484%** |

粗体 = 实际会同时出现的组合(线宽 ramp 挂 style zoom,深放大必配最粗档,
所以左下角"细线+大 texelPx"是不可达格)。**幽灵全表 0.000%。**

**三条结论:**

1. **实际最坏 ≈ 1.5%,发生在 z19 级深放大**;常用段(d≤2)≤0.06%。
2. **量化与端点夹皆无责**:去掉 RGBA8 量化 0.055%→0.058%(噪声内),
   去掉 `kLineFieldClampMaxTexels=1.5` 端点夹**数字一字不变**。
   → 这两个常数尺寸正确,不是债,别去调。
3. 漏画中 **64-88% 是容量**(真最近要素根本不在该像素的 2×2 块里),
   其余是同要素的邻段几何复现不准。

**裁决:不修。** 双线编码(+16MB 场显存、FS 4→8 次 fetch)最多吃掉容量那
64-88%,即把 z19 的 1.48% 压到 ~0.4%,常用段从 0.05% 压到 0.01% —— 买回的量级
不值这个价。真机深放大观感报怨再启。

**已否掉的免费方案(勿再提):烘焙侧仲裁。** 思路是 stamp 时留亚军,补一趟
修复 pass,在"冠军要素在该像素 4 个 2×2 块里都另有代表"时改判亚军 ——
零显存零 FS。实测 **0.040% → 0.359%,负收益 9 倍**。
死因:**要素级冗余 ≠ 几何级冗余**。邻居纹素记的是同一条路的*另一段*,
它复现不出本地那截几何;换掉冠军是零和的,让出去的比补回来的多。
连"可证无害"的严格块覆盖判据(四块逐块验证 + 奇偶四趟应用)也救不回来。

## E3. 复查记录:兜底路径冒充主路径(2026-08-14)

**触发**:讨论 V5 时实测 `d`(场纹素放大级数)的分布,发现问题范围远超判据描述。

### 实测数据(默认 30km 视角,release,真机)

```
V5DIAG fieldPages=25  d0=480 (8%)   d1=0   d2=5220 (92%)   d3+=0
```

`d = 影像页zoom − 场页zoom`,`texelPx = 2^d`。d=2 → 场纹素 = 4 屏幕像素。

### 后果链(一个根因,三条判据同时假绿)

```
d=2 (92% 画面)
 ├─ wEff = max(ramp 1.05~3.15, 0.6×4=2.4) → 取 2.4 常数 ⇒ V3 假恒定 + V4 分级失效
 └─ aa   = max(0.5,            0.35×4=1.4) → 取 1.4       ⇒ V5 软
```

**连带解释了两件历史误判**:
- 「线太粗」→ 我调细三档 ramp(`368b9cce4`),但那 92% 的画面根本不看 ramp,粗细由兜底定;
- 步2 收官测「远/中/近线宽都差不多」→ 我归因成"斜线扫描测量偏差",**实际是真的没分级**。

### 兜底点全面审计(整条场链)

只有上述两个是**功能性**兜底(常态生效);其余(`max(rms,1e-6)`、`clamp(uvIn)`、
`clamp(cell)`、`fz` 的 df≤6 约束等)均为防御性,正常路径不触发,已逐个确认。
`band=8 texel`(d=2 时覆盖 32px)与 R8 量化(0.125 屏幕像素/级)均已排除。
**根因唯一:标量距离场在放大时无法被双线性插值正确重建。**

### 补充证据:主路径失效的程度(数值模拟,2026-08-14)

`scratchpad/vdf_sim.py` 在 texelPx=4(=实测 d=2)下,用**真实解算参数**
(半宽 1.2px、AA 0.5px、**兜底去掉**)重建各类几何:

- **标量场 +0.36px 系统性高估(100% 高估),渲染出来是一片空白** ——
  即当前实现在 92% 的画面里,**主路径完全画不出线**,屏幕上能看见路网
  全靠 `0.6×texelPx` 把阈值抬到 2.4px。不是"部分失效",是彻底失效。
- 高估的机制:距离场在线心是 V 形尖点,双线性插值跨尖点必然取到两侧的
  较大值 → 线被"吃掉"。这是标量距离场放大时的**固有性质**,不是参数问题。

### 元规则(新增,适用于所有判据)

> **带兜底 / 下限 / clamp 的机制,验收必须证明兜底没有生效**——只看"结果没崩"
> 会把兜底路径的稳定性当成主路径的正确性。V3/V4/V5 三条判据同时踩这个坑。
> 落实方式:这类判据的验收要附一个**主路径命中率**(如本次的 d 分布直方图)。

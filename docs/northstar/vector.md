# 矢量模块北极星 — 产品体验判据

**这份文档回答「做到什么程度算好、现在到哪了」。**
不回答「代码在哪」(那是 `AI_INDEX.md`),也不回答「当时怎么修的」(那是 `docs/issues/*`)。
`docs/issues/` 是写完即冻结的历史档案;**本文是活的**,随每次专项收官更新。

## 怎么用(这是本文的主要价值)

- **判据编号(V1…)是稳定引用锚点。** 你可以直接说「V3 我不满意」「V9 提前做」,
  不必重新描述一遍观感;我开工前会引用「本次动 V3/V4」,收官后改状态并附证据。
- **状态**:✅ 达成(有证据) ⚠️ 部分达成/有已知缺口 ❌ 未做 🔒 待你拍板
- **类型决定谁说了算**:
  - 【机制】我能自证 —— 命令输出、计数、测试红绿、帧时。我负责给数,不需要你看。
  - 【观感】像素判断**归你** —— 我只负责钉死复现场景 + 给截图,不替你判定"好看"。
- **「代价」列是硬要求**:每条体验都要写清花了多少(GPU/CPU/内存),因为你认可的
  准则是「体验达标**且最便宜**」——只写达没达成,就没法判断值不值、还有没有余量。
  **没量化过就写「未量化」,不许填"应该很小"**;这类空头承诺会沉淀成 C.5 的债。
- **性能债编号(P1…)** 与判据编号同为引用锚点,见 C.5。
- **改状态必须附证据**(commit / 真机数据 / 截图),不能凭印象改。
- **`推断` 标记**:凡带此标记的判据是我从现状与对照系推出的,**不是你说过的**,
  优先请你校对——校错了比没写更糟。

## 北极星一句话

> 在 **45° 斜视 + 地平线在屏**的 3D 地形上,线的观感**超过 maplibre 的任何一种模式**:
> 拿到平面模式的线宽恒定与锐度,同时不付平面模式"没有 3D"的代价,
> 也不落进地形 RTT 模式"两次重烘之间线宽在漂"的病。

**这不是口号,是机制差异,已在 `.ref` 源码核实**(见下方对照表)。
对照系为什么是 maplibre 而不是 Google Earth:GE 的矢量是预烘影像,
我们要的是**运行期可换样式/可编辑**的矢量,GE 那条路不可比。

### 水位线对照(三方)

| 维度 | maplibre 平面模式 | maplibre 地形 RTT | **本引擎** |
|---|---|---|---|
| 线宽随相机连续恒定 | ✅ 屏幕空间逐帧画 | ❌ **两次重烘之间是位图拉伸** | ✅ **FS 内逐像素解析解算** |
| 重烘触发 | 不需要 | 源瓦集合/数据版本变才重烘,**指纹不含 zoom** | **不需要**(z 封顶后零重烘) |
| 3D 地形贴合 | ❌ 没有地形 | ✅ | ✅ |
| 任意俯仰角 / 地平线在屏 | — | 受限(病被放大故回避) | ✅ 45° 斜视为默认姿态 |
| 放大时锐度 | ✅ 矢量重画 | ❌ 纹理放大糊 | ✅ SDF 解析放大(**V5 有余债**) |
| GPU 成本 | 独立 draw | 独立 RTT pass + FBO | **~0(寄生地形 FS)** |

> **关键出处**:`.ref/maplibre-gl-js/src/webgl/render_to_texture.ts:114-127` ——
> RTT 失效指纹 = `sorted_tile_keys#revision`,**只含源瓦集合与数据版本,不含 zoom
> 或任何相机参数**。故 z14.0 连续推到 z14.9 的全过程 RTT 不重烘,线宽按纹理比例
> 放大 = 屏幕像素不恒定。这是它的结构性病,不是参数没调好。

### 但「超越」目前**只在 8% 的画面成立**(2026-08-14 复查修正)

| 已兑现 | 未达标 |
|---|---|
| 零重烘(V14)、~0 GPU(V2)、3D 任意俯仰角、**机制上具备**像素恒定的能力 | **线宽像素恒定(V3)实测只在 8% 画面走主路径**,其余 92% 由纹素兜底接管 = **行为等同 maplibre RTT 位图放大**;**V4 分级宽度未生效**;**V5 软**;V9 dash / V20 Metal 未做 |

> ⚠️ **上一版这里写的是"线宽像素恒定 ✅ 已兑现",是错的。** 详见 E3 复查记录:
> 判据绿是因为兜底路径稳定,不是因为主路径正确。**在拿到 d≈0 之前,
> 不得对外宣称"超越 maplibre"。**

## C. 性能北极星(预算 / 实测 / 债)

> **准则**:优化只走「消除浪费」,**不走降低可见细节**——限帧、降 LOD、缩短可见
> 距离都不算优化。矢量三分工的整个架构就是这条准则的产物:面/线的 GPU 成本不是
> 被"调低"的,是被**换了表示**换掉的。

### C.1 帧预算(60fps = 16.7ms) `推断`

| 阶段 | 预算 | 当前实测(2026-08-14 步3 后) | 余量 |
|---|---|---|---|
| FrameLoop total(手势期,无偏采样) | < 16.7ms | **6.9 / 8.1ms**(n=2,见下方采样陷阱) | 大 |
| engine(CPU 侧) | < 6ms | p50 **3.69ms**,max 7.95ms | 有 |
| **慢帧率**(total ≥ 25ms) | < 1% `推断` | **2.1%**(5/241 帧) | **超** → 见 P6 |
| 矢量专属 GPU pass | 个位数 ms | **0.01ms** | 大 |
| terrain pass(含面+线场解算) | 不高于纯影像基线 | **3.62-4.18ms** vs 刀2 记录基线 3.3ms | 同量级 |
| GPU total(手势期) | < 16.7ms | **7.80-9.02ms**(尖峰帧 13.94) | 有 |

> **⚠️ 采样陷阱(踩过一次,写下来防复发)**:`FrameLoop` 日志的打印条件是
> `frameId<=3 || frameId%120==0 || total>=25ms || swap>=8ms` ——
> **它是异常捕获,不是随机采样**。直接对日志行算 p50 会把慢帧当分母,
> 得出"p50=20.6ms 超标"的假结论(真值 6.9-8.1ms)。只有 `%120==0` 那批无偏。

**预算是我推断的,请校对**:我按 60fps 反推,但你的实际目标可能是 30fps 稳定
优先于 60fps 抖动。这条定不下来,后面所有"还有没有余量"的判断都会偏。

## E. 已判死 / 勿再提(边界)

**这一节的作用是防止日后重复提议已被否决的方案。** 要推翻需要新证据,不是新想法。

| 方案 | 死因 |
|---|---|
| 墙带 + 深度带裁剪单 pass(W) | 50-65ms 比 stencil 差 4×,且肥线晃边;结构性死因=墙面片元×重 FS |
| 独立 overlay pass 画矢量 | 实测 25-30ms,不可接受 |
| 面 / 建筑进 SDF 场 | 面要「归属+颜色」非「距离」;建筑 Nyquist 死局(10-50m 楼 vs ~10m/texel) |
| 场解算分母用 `fwidth(fieldV)` | 线心是场脊、导数→0 → 沿线心挖洞(真机复现) |
| 场解算分母用 `dFdx(sampleUv)` | span 边界回绕爆导数 → 沿 cell 网格白虚线(真机复现) |
| 矢量线宽烘进场纹素 | 与「屏幕像素恒定」冲突,已被 V3 取代 |

> TBDR 铁律(判死上述方案的依据):**pass 数不是成本,片元数 × FS 重量才是。**

## E2. 校对记录:立项预判 vs 实际(场线宽专项,2026-08-14)

> **这是本文「方便日后校对」的第一个真实案例。** 留着它不是为了记账,
> 是为了下次做架构预判时知道**自己在哪类判断上容易失准**。

当初立项原话的逐条兑现情况:

| # | 立项预判 | 实际 | 判 |
|---|---|---|---|
| 1 | 场语义从「烘死宽度的覆盖」改成「到中心线的距离」 | 完全照此实施(`value = 1 − dist/band`) | ✅ |
| 2 | **「宽度阈值在 FS 里按 `fwidth` 换算成真屏幕像素」** | **机制错**:`fwidth(fieldV)` 不可用——场值在线心是**脊**,脊上导数→0,eps 兜底把线心判成"远"→ 沿线心周期性挖洞。正解=对**几何量 g**(跨 cell 连续的仿射)取屏幕导数 ÷span,不能对场值取 | ❌ |
| 3 | 近远景、祖先页全部自动补偿 | 兑现,四态实测 ~4px | ✅ |

## E3. 复查记录:兜底路径冒充主路径(2026-08-14)

**触发**:讨论 V5 时实测 `d`(场纹素放大级数)的分布,发现问题范围远超判据描述。

### 实测数据(默认 30km 视角,release,真机)

```
V5DIAG fieldPages=25  d0=480 (8%)   d1=0   d2=5220 (92%)   d3+=0
```

`d = 影像页zoom − 场页zoom`,`texelPx = 2^d`。d=2 → 场纹素 = 4 屏幕像素。

### 后果链(一个根因,三条判据同时假绿)

```
d=2 (92% 画面)
 ├─ wEff = max(ramp 1.05~3.15, 0.6×4=2.4) → 取 2.4 常数 ⇒ V3 假恒定 + V4 分级失效
 └─ aa   = max(0.5,            0.35×4=1.4) → 取 1.4       ⇒ V5 软
```

**连带解释了两件历史误判**:
- 「线太粗」→ 我调细三档 ramp(`368b9cce4`),但那 92% 的画面根本不看 ramp,粗细由兜底定;
- 步2 收官测「远/中/近线宽都差不多」→ 我归因成"斜线扫描测量偏差",**实际是真的没分级**。

### 兜底点全面审计(整条场链)

只有上述两个是**功能性**兜底(常态生效);其余(`max(rms,1e-6)`、`clamp(uvIn)`、
`clamp(cell)`、`fz` 的 df≤6 约束等)均为防御性,正常路径不触发,已逐个确认。
`band=8 texel`(d=2 时覆盖 32px)与 R8 量化(0.125 屏幕像素/级)均已排除。
**根因唯一:标量距离场在放大时无法被双线性插值正确重建。**

### 补充证据:主路径失效的程度(数值模拟,2026-08-14)

`scratchpad/vdf_sim.py` 在 texelPx=4(=实测 d=2)下,用**真实解算参数**
(半宽 1.2px、AA 0.5px、**兜底去掉**)重建各类几何:

- **标量场 +0.36px 系统性高估(100% 高估),渲染出来是一片空白** ——
  即当前实现在 92% 的画面里,**主路径完全画不出线**,屏幕上能看见路网
  全靠 `0.6×texelPx` 把阈值抬到 2.4px。不是"部分失效",是彻底失效。
- 高估的机制:距离场在线心是 V 形尖点,双线性插值跨尖点必然取到两侧的
  较大值 → 线被"吃掉"。这是标量距离场放大时的**固有性质**,不是参数问题。

### 元规则(新增,适用于所有判据)

> **带兜底 / 下限 / clamp 的机制,验收必须证明兜底没有生效**——只看"结果没崩"
> 会把兜底路径的稳定性当成主路径的正确性。V3/V4/V5 三条判据同时踩这个坑。
> 落实方式:这类判据的验收要附一个**主路径命中率**(如本次的 d 分布直方图)。
